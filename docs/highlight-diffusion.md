# 泛光与光晕

`ColorRecipeParams.bloom` 控制泛光，`redHalation` 控制界面中的光晕，范围仍为
0–1；0 表示关闭。JSON、预设和数据库字段保持兼容，旧配方加载后使用新算法，因此
相同强度的外观会改变。历史 `halation` 字段属于已停用的 HDF，并非当前光晕入口。

预览、录像和照片导出共用 `HighlightDiffusionGl`。两种效果均从完成调色的二维纹理
生成扩散图，先光晕、后泛光，再进入原有最终颗粒步骤。原有 Video Log 的前置颗粒
策略保持不变。光晕不再在照片导出的调色前提取高光。

## 算法与参数

依据本地 Snapseed 4.1.6 的 Bloom / Halation 静态分析，保留其默认形态参数，现有
滑杆只改变合成强度。输入是显示编码 RGB；合成时使用参考实现的 2.2 次幂转换。

| 参数 | 泛光 Bloom | 光晕 Halation |
| --- | --- | --- |
| 工作图最长边 | 256，保持比例，不放大小图 | 512，保持比例，不放大小图 |
| 高光来源范围 | 40 | 20 |
| 高光阈值 | 0.598 | 0.794 |
| 模糊尺寸参数 | 70 | 25 |
| 高斯 σ / 截断半径 | 17.5 / 52 像素 | 5 / 15 像素 |
| 形态参数 | softness 50，合成 gamma 2.2 | hardness 20，幂指数 1.25 |
| 颜色与其他参数 | 保留高光颜色 | hue 0 → RGB (1, 0.05, 0.05)，graininess 50，destinationRange 100，globalShift 0 |

共同高光遮罩：`M = clamp((Y − T) / (1 − T), 0, 1)`，其中
`Y = dot(C, (0.299, 0.587, 0.114))`，按工作图像素中心最近邻提取输入。

- 泛光对 `C × M` 做高斯模糊，再除以全图 RGB 最大值。强度 ≤ 0.5 时，在原图与
  gamma 域完整泛光之间插值；强度 > 0.5 时，提高 gamma 域的泛光能量。
- 光晕只模糊 `M`，以全图最大值的三分之一归一化，施加以 0.4 为分界的硬度曲线。
  遮罩截断为 8 位值后再进行全分辨率插值；合成时叠加红色、空间颗粒和目标亮度门控。
- 峰值为零时明确生成全零扩散图，避免除零。强度 ≤ 0.001 时不执行对应效果，与现有
  预览开关精度保持一致。

## GPU 实现

高光提取、水平/垂直模糊、最大值归约、归一化、合成均在同一 GLES context 完成，
不回读峰值。高斯核用相邻权重配对及线性采样减少采样次数；边界为 clamp-to-edge。
最大值逐级以 2×2 归约到 1×1，奇数尺寸向上取整并覆盖末行、末列。

模糊及归约使用 RGBA16F，光晕遮罩及最终输出使用 RGBA8；泛光归一化图使用 RGBA16F。
这保留弱高光，但与参考 CPU 浮点计算存在半精度舍入差异，不承诺逐像素一致。
各 pass 读写不同纹理；两效果分别拥有输出纹理，避免同时开启时产生纹理反馈。
尺寸变化重建目标，context 丢失清空句柄，正常释放删除 program / texture / framebuffer。

## 验证

2026-09-09：`./gradlew compileDefaultDebugKotlin` 通过。

在 PMA110 / Adreno 840 / GLES 3.2 V@0842.44 上，以独立可执行程序运行生产 GLSL，
验证实际 compile/link、RGBA16F 分配、draw、归约、后续采样与 readback。
60 组检查涵盖黑图、低亮度图、白图、彩色高光、边缘高光、横竖图、奇数尺寸、1×1、
1×33，以及 0 / 0.25 / 0.5 / 0.75 / 1 强度。

- 泛光归一化图与独立双精度逐 tap CPU 实现最大误差 0.001363；最终输出最大误差
  0.003202（归一化 RGB）。
- 光晕遮罩最大误差 1/255；最终输出通过 CPU 公式的颗粒上下界检查，最大超界误差
  0.003405。未将 CPU `sin` 的随机数结果作为跨驱动逐像素判据。
- 所有输出有限；零强度、黑图和阈值以下图像保持不变。

此外，通过 `app_process` 加载项目实际编译的 `HighlightDiffusionGl` 与着色器类，
验证 1×1、17×9、513×259、259×513、1920×1080 尺寸切换、效果开关、连续帧复用、
两效果组合与分别串联的像素一致性，以及 context 丢失和 release 后重建。
诊断仅替换日志和基础 shader 编译包装，不替换生产组件的调度与资源管理逻辑。

上述诊断不安装 APK、不运行 Android Test。尚未进行 App 内取景与成片目视对比，
也未验证 Mali 等其他驱动上的实际渲染表现。

## Media3 视频播放与导出

后续检查发现，相机录像使用的 `LutRenderer` 和相册使用的 `VideoLutEffect` 是独立
链路；上面的首次重构只接通前者。现已在 `VideoLutEffect` 中读取 `bloom` /
`redHalation`，通过 `VideoHighlightDiffusionGl` 接入同一扩散组件。覆盖调用此 effect 的
相册视频播放、动态照片播放、视频编辑预览、视频导出和动态照片视频片段处理。

启用时，色彩/LUT/锐化先写入 RGBA8 中间纹理，随后执行光晕、泛光和最终颗粒，再写回
Media3 管理的输出 framebuffer。主调色 pass 暂停颗粒，避免重复添加或让颗粒参与
高光提取。关闭两项时保留原单 pass 路径。输出 framebuffer、read framebuffer、
viewport 和外部 VAO 在返回及异常路径恢复；处理失败转换为带时间戳的
`VideoFrameProcessingException`，不静默输出缺失效果的视频。

已核对项目依赖的 Media3 1.10.0 本地源码：默认 SDR 工作空间使用显示编码 RGB，
与此算法一致；HDR 输出使用线性工作空间。当前两项只支持 SDR；若 `useHdr=true`
且启用了任一项，会明确报告不支持，不能把此实现视为 HDR 泛光算法。

接入后 Kotlin 编译通过。新增 Media3 适配层的独立设备诊断进程被系统以 SIGKILL
终止（exit 137，限制 Java 堆重试亦然），日志未确认具体原因，不能认定为渲染验证
通过。未进行完整的视频解码、播放和编码导出验证；先前的 60 组检查与 context 恢复
结果仅证明共用扩散组件，不能替代该视频适配层的端到端验证。
